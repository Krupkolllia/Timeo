# Timeo — техническое задание

Приложение учёта смен и расчёта зарплаты. Замена SuperShift для одного конкретного человека.
Документ является источником истины для разработки. Все решения ниже согласованы с заказчиком и не подлежат
переизобретению без явного распоряжения.

---

## 1. Контекст

**Кто пользователь.** Отец заказчика. Взрослый человек, уверенно пользуется телефоном, но не разработчик.
Сейчас пользуется бесплатной версией SuperShift на iPhone 13 Pro.

**Устройство.** iPhone 13 Pro. Единственное целевое устройство. Приложение ставится на домашний экран через
Safari → Поделиться → «На экран "Домой"». Ориентация портретная. Десктоп и планшет не поддерживаем осознанно,
но интерфейс не должен ломаться, если открыть на широком экране.

**Язык.** Русский. Все тексты вынесены в один файл словаря, чтобы можно было добавить польский позже.

**Валюта.** Злотый (zł) по умолчанию, переключается в настройках.

**Название.** Timeo. Это же имя на иконке домашнего экрана.

**Стоимость.** Ноль. Бесплатные тарифы Cloudflare, Supabase, GitHub.

**Чего не требуется.** Mac, Xcode, Swift, аккаунт Apple Developer, публикация в App Store, TestFlight.
Это обычный сайт, который открывается в Safari и ставится на домашний экран. Разработка ведётся
на любой операционной системе.

---

## 2. Ключевые требования заказчика

1. Интерфейс интуитивный и предсказуемый.
2. Базовая ставка задаётся отдельно на каждый месяц. Изменение ставки в текущем месяце не пересчитывает прошлые.
3. Пользователь задаёт свои ставки в валюте за час и меняет их для сверхурочных, выходных, праздников.
4. Максимальная гибкость. Никакой жёсткой валидации. На любой нестандартный случай должно найтись решение.

---

## 3. Принятые решения

| Вопрос | Решение |
|---|---|
| Хранение данных | Local-first: IndexedDB на телефоне, автоматический бэкап в Supabase |
| Что считаем | Только брутто: часы × ставка. Никаких налогов и ZUS |
| Режим работы | Журнал факта, не планировщик. Цифра внизу — уже заработанное |
| Расчётный период | Настраиваемый: «период начинается с N числа», по умолчанию 1 |
| Именование периода | По месяцу, в котором период заканчивается. Переключается галочкой |
| Ввод дня | Количество часов (по умолчанию 8) + множитель + ставка. Время начала/конца — опционально, выключено |
| Множители | Множитель и абсолютная сумма за час связаны, редактируются оба |
| Выходные и праздники | Множитель подставляется автоматически, виден на экране дня, правится в один тап |
| Отпуск, больничный, отгул | Отдельные типы дней с настраиваемым способом оплаты |
| Мест работы | Одно. Поле в БД заложено, в интерфейсе не показывается |
| Вход | Почта + пароль и кнопка «Войти через Google» |
| Уведомления | Ежевечернее напоминание, только если день не заполнен. Время настраивается, можно выключить |
| Оформление | Переключатель тема, по умолчанию системная |
| Импорт из SuperShift | Не делаем. Только ручной ввод итогов за прошлые месяцы |

## 4. Стек

**Фронтенд.** React + TypeScript + Vite. Tailwind. Роутинг — минимальный, экранов немного.
Состояние — Zustand или контекст, без Redux.

**PWA.** vite-plugin-pwa. Manifest с именем Timeo, иконками 192/512, `display: standalone`,
`theme-color`, apple-touch-icon. Service worker кеширует оболочку приложения, приложение полностью
работоспособно офлайн.

**Локальное хранилище.** IndexedDB через Dexie. Это первичное хранилище. Всё, что видит пользователь,
читается отсюда. Никаких спиннеров при открытии.

**Облако.** Supabase Postgres. Схема повторяет локальную. Синхронизация фоновая, не блокирующая.
Row Level Security по `user_id`. Разрешение конфликтов — последняя запись побеждает по `updated_at`,
плюс журнал изменений для отладки.

**Уведомления.** Здесь есть подводный камень, который надо учесть на этапе проектирования. В PWA нет
способа запланировать локальное уведомление на будущее время: API отложенных уведомлений в Safari
отсутствует, а service worker не просыпается сам по расписанию. Единственный работающий путь — Web Push
с сервера. Значит:

- при включении напоминаний приложение запрашивает разрешение и сохраняет push-подписку в Supabase
- Cloudflare Worker по расписанию раз в час смотрит, у кого наступило заданное время напоминания
- Worker проверяет в Supabase, есть ли у этого пользователя запись за сегодняшний день, и шлёт пуш
  только если записи нет
- отсюда следствие: **напоминания работают только при включённой синхронизации и выполненном входе.**
  Без аккаунта серверу неоткуда узнать ни адрес устройства, ни заполнен ли день

Это надо честно показать в интерфейсе: переключатель напоминаний у неавторизованного пользователя
объясняет, что для них нужен вход.

**Хостинг.** Cloudflare Pages, автодеплой из приватного репозитория GitHub. Адрес вида `timeo.pages.dev`.

**Keep-alive.** Cloudflare Worker с cron-триггером раз в сутки делает запрос к Supabase.
Бесплатные проекты Supabase засыпают после недели без активности, это страховка.

## 5. Модель данных

Все таблицы имеют `id` (uuid), `user_id`, `created_at`, `updated_at`, `deleted_at` (мягкое удаление
ради синхронизации).

**Работа без аккаунта.** Приложение полностью функционально до всякого входа: это требование, а не
временное упрощение. Пока пользователь не вошёл, `user_id` заполняется локальным uuid, который
генерируется при первом запуске. При первом входе в аккаунт все локальные записи переписываются на
настоящий `user_id` и уезжают в облако. Обратная ситуация (в облаке уже есть данные, а локально другие)
разрешается предложением выбрать, что оставить, а не молчаливым слиянием.

### 5.1 `settings`

Одна строка на пользователя.

- `currency` — по умолчанию `PLN`
- `period_start_day` — 1..28, по умолчанию 1
- `period_naming` — `end_month` | `start_month`
- `default_hours` — по умолчанию 8
- `theme` — `system` | `light` | `dark`
- `show_shift_times` — bool, по умолчанию false
- `reminder_enabled`, `reminder_time`
- `week_starts_on` — понедельник
- `weekend_multipliers` — множители для субботы, воскресенья, праздника
- `default_base_rate` — ставка, с которой создаётся период, если предыдущего периода не существует,
  а также место, куда пишется новая ставка при выборе «применить со следующего периода»
- `default_norm_hours` — то же самое для нормы часов
- `preferred_rate_change_mode` — запомненный ответ на вопрос о смене ставки

### 5.2 `periods`

**Ключевая таблица. Реализует требование №2.**

- `year`, `month` — идентификатор периода
- `base_rate` — базовая ставка за час
- `norm_hours` — норма часов за период, для показателя «осталось до нормы»
- `extra_amount`, `extra_note` — прочие доплаты и вычеты за период
- `is_closed` — период закрыт, цифры зафиксированы
- `closed_totals` — снимок итогов на момент закрытия
- `is_manual` — период заведён вручную как историческая запись, дни не заполняются

**Механика изоляции.** При первом обращении к новому периоду создаётся строка, в которую копируются
значения из предыдущего периода. Копируются, а не наследуются по ссылке. Изменение `base_rate` в периоде
за август физически не может повлиять на строку за июль. Если предыдущего периода не существует
(первый запуск, или отец пролистал календарь на год вперёд), берутся `default_base_rate`
и `default_norm_hours` из настроек.

### 5.3 `day_types`

Шаблоны того, чем может быть день.

- `name`, `color`, `icon`
- `pay_mode` — `hourly` (часы × ставка) | `fixed_amount` (фиксированная сумма за день) | `unpaid` (ноль)
- `fixed_amount` — сумма для режима `fixed_amount`
- `counts_as_work` — bool, попадают ли часы этого дня в показатель «всего часов»
- `counts_toward_norm` — bool, засчитывается ли день в норму часов. Для отпуска обычно true при
  `counts_as_work` false: в норму идёт, в отработанные часы нет
- `default_hours`
- `default_multiplier`, `default_rate`
- `ignore_auto_multipliers` — bool. Если true, множители выходных и праздников к этому типу не применяются.
  Нужно для отпуска и больничного: отпуск, выпавший на воскресенье, не должен внезапно оплачиваться вдвойне
- `sort_order`, `is_archived`

Предустановленные: Рабочий день, Ночная смена, Отпуск, Больничный, Отгул, Выходной.
Все переименовываются, удаляются и создаются заново пользователем.

### 5.4 `entries`

Запись за конкретную дату. Допускается несколько записей на один день.

- `date`
- `day_type_id`
- `hours` — основное поле ввода
- `multiplier`
- `rate_per_hour` — ставка, применённая к этой записи. Заполняется **всегда**, в том числе при
  автоматическом расчёте
- `rate_is_manual` — bool. Отличает ставку, вписанную пользователем, от ставки, зафиксированной системой
  при изменении базовой ставки. Без этого флага обе выглядят одинаково и пересчёт периода работает неверно
- `amount` — рассчитанная сумма
- `amount_override` — если заполнено, перебивает расчёт полностью
- `start_time`, `end_time`, `break_minutes` — опциональные, показываются только при `show_shift_times`
- `note`
- `rate_source` — откуда взялась ставка: база периода, правило выходного, ручной ввод. Нужно для экрана расшифровки

**Привязка к периоду.** Запись не хранит ссылку на период, он вычисляется из `date` и `period_start_day`.
Отсюда следует опасный сценарий: изменение `period_start_day` задним числом перекидывает записи между
периодами, в том числе закрытыми. Поэтому изменение границы периода запрещено, если существует хотя бы один
закрытый период. Пользователю показывается объяснение и предложение сначала открыть периоды.

**Важно.** В записи хранятся одновременно множитель и получившаяся сумма. Это позволяет и пересчитывать
при изменении ставки, и зафиксировать историю при закрытии периода.

### 5.5 `holidays`

- `date`, `name`, `is_custom`

Предзагружается список польских государственных праздников. Полностью редактируемый: можно удалить,
добавить свой день, отметить корпоративный выходной.

## 6. Логика расчёта

### 6.1 Расчёт одной записи

```
если amount_override заполнено:
    сумма = amount_override

иначе если pay_mode = unpaid:
    сумма = 0

иначе если pay_mode = fixed_amount:
    сумма = fixed_amount типа дня

иначе (pay_mode = hourly):
    если rate_is_manual:
        ставка = rate_per_hour
    иначе:
        ставка = base_rate периода × multiplier
        rate_per_hour := ставка   // сохраняем результат в запись
    сумма = часы × ставка
```

### 6.2 Определение множителя при создании записи

Порядок применения, первое сработавшее правило побеждает:

1. Если у типа дня взведён `ignore_auto_multipliers` → множитель типа дня, дальше не смотрим
2. Праздник из таблицы `holidays` → множитель праздника из настроек
3. Воскресенье → множитель воскресенья
4. Суббота → множитель субботы
5. Множитель, заданный в типе дня
6. Иначе 1.0

Множители **никогда не перемножаются между собой**. Ночная смена ×1.5 в воскресенье ×2 не даёт ×3.
Побеждает одно правило, и пользователь видит, какое именно. Если нужен именно ×3, он вписывает 3 руками.

Подставленное значение **всегда видно на экране дня** с подписью источника, например «воскресенье, ×2».
Ничего не считается скрытно. Пользователь меняет значение прямо там, одним тапом.

### 6.3 Изменение базовой ставки

При сохранении новой `base_rate` показывается выбор из трёх вариантов:

- **Пересчитать весь период.** Все записи периода с `rate_is_manual = false` пересчитываются.
- **Применить с указанной даты.** Записям до этой даты проставляется `rate_is_manual = true` с текущим
  значением `rate_per_hour`, после чего они перестают зависеть от базовой ставки. Записи после даты
  пересчитываются.
- **Применить со следующего периода.** `base_rate` текущего периода не меняется. Новое значение
  записывается в `default_base_rate` настроек и подхватится при создании следующего периода.
  Записи текущего периода не трогаются.

Выбор запоминается в `preferred_rate_change_mode` и предлагается по умолчанию, но диалог показывается каждый раз.

**Инвариант, который нельзя нарушать: никакая операция не изменяет суммы в периодах, отличных от текущего.**

### 6.4 Итог за период

```
сумма          = Σ сумм записей периода + extra_amount
всего часов    = Σ часов записей, где counts_as_work = true
часов к норме  = Σ часов записей, где counts_toward_norm = true
осталось       = norm_hours − часов к норме
```

Для периодов с `is_manual = true` суммирование не выполняется вообще: записей у них нет,
итог берётся напрямую из `closed_totals`.

Закрытие периода записывает итог в `closed_totals`. После этого никакие изменения настроек,
правил или ставок на него не влияют.

## 7. Экраны

### 7.1 Календарь (главный)

Сетка месяца, неделя с понедельника. В ячейке дня — цветная метка типа дня и количество часов мелким шрифтом.
Праздники и выходные визуально отличаются.

Сверху: название периода, стрелки переключения, тап по названию открывает выбор месяца и года.

Снизу закреплённая панель:
- крупно: сумма за период и всего часов
- строкой выше мелко: сравнение с прошлым периодом (например «+340 zł») и остаток до нормы часов
- тап по панели разворачивает подробную сводку

### 7.2 Экран дня

Открывается тапом по дню. Выезжает снизу, не занимает весь экран.

- Крупные кнопки типов дней, тап проставляет день целиком со значениями по умолчанию
- Поле часов, уже заполнено значением по умолчанию, крупные кнопки −/+ и прямой ввод
- Поле множителя и поле ставки за час, связанные между собой
- Подпись, откуда взялся множитель
- Итоговая сумма за день, пересчитывается на глазах
- Заметка
- Переключатель «указать сумму вручную»
- Время начала и конца — только если включено в настройках

### 7.3 Сводка периода

Построчная расшифровка: каждая запись с датой, часами, ставкой, множителем и суммой. Внизу итог.
Отсюда — кнопка «закрыть период» и поле прочих доплат.

### 7.4 Настройки

Здесь только то, что не привязано к периоду: ставка **для новых периодов**, норма часов для новых периодов,
множители выходных и праздника, начало расчётного периода, валюта, тема, значение часов по умолчанию,
напоминания, экспорт в файл, вход в аккаунт.

Базовая ставка и норма часов **конкретного** периода правятся на экране сводки этого периода, а не здесь.
Иначе непонятно, какой месяц редактируется, и требование об изоляции периодов нарушается визуально,
даже если технически соблюдено.

### 7.5 Типы дней

Список с перетаскиванием для сортировки, редактирование каждого типа.

### 7.6 Праздники

Список по годам, добавление и удаление.

### 7.7 Прошлые периоды

Ручной ввод исторических данных: выбрать месяц, вписать часы и сумму, сохранить как закрытый период.
Дни при этом не заполняются.

### 7.8 Экспорт и восстановление

Кнопка сохранения всех данных в один файл JSON. И, что важнее, кнопка загрузки такого файла обратно:
резервная копия без возможности восстановления смысла не имеет. При загрузке пользователь выбирает,
заменить данные целиком или добавить недостающее. Формат файла содержит номер версии схемы,
чтобы старый файл можно было прочитать будущей версией приложения.

## 8. Гибкость и валидация

Требование №4 реализуется так:

- **Ни одно поле не блокирует сохранение.** Разрешены 26 часов в сутки, отрицательные суммы,
  ставка 0, несколько записей на один день, отпуск в воскресенье.
- **Вместо ошибок — мягкие подсказки.** Серая строка «больше 24 часов, это точно верно?», которую
  можно игнорировать. Никаких красных рамок и модальных окон.
- **Любое вычисленное значение перебивается вручную.** Часы, ставка, множитель, итоговая сумма дня,
  итог периода.
- **Предсказуемость обеспечивается прозрачностью, а не запретами.** Экран сводки всегда показывает,
  из чего сложилась цифра, построчно.
- **Ничего не удаляется мгновенно.** Удаление показывает плашку «отменить» на несколько секунд.

## 10. План работ

Порядок блоков подобран так, чтобы каждый следующий можно было отрезать, не ломая предыдущие.
После каждого блока — коммит и деплой.

### Блок 0 — фундамент

Приватный репозиторий, `.claude/settings.json` с запретами на разрушающие команды, `CLAUDE.md`,
скелет Vite + React + TS + Tailwind, PWA-манифест и иконки, деплой на Cloudflare Pages.
Результат: по адресу открывается пустая страница с надписью Timeo, которая ставится на домашний экран.

### Блок 1 — хранилище и календарь

Dexie, схема таблиц, сетка месяца, переключение периодов, предустановленные типы дней.

### Блок 2 — экран дня и расчёт

Ввод часов, множитель, ставка, ручное переопределение суммы, расчёт по разделу 6.

### Блок 3 — периоды и ставки

Копирование настроек в новый период, диалог изменения базовой ставки, закрытие периода.

### Блок 4 — праздники и автомножители

Список польских праздников, правила подстановки, экран редактирования.

### Блок 5 — сводка и экспорт

Построчная расшифровка, прочие доплаты, сохранение копии в файл и восстановление из файла,
ручной ввод прошлых периодов.

### Блок 6 — настройки

Все переключатели раздела 7.4, тема, валюта, границы периода.

### Блок 7 — облако

Supabase, схема, RLS, вход по почте и через Google, синхронизация, миграция локальных данных.

### Блок 8 — уведомления

Push-подписка, Worker с расписанием, проверка заполненности дня.

### Блок 9 — keep-alive и полировка

Cron-воркер против засыпания Supabase, мелкие правки по замечаниям.

### Проверка на устройстве

Первую установку на iPhone отца делаем сразу после блока 0, до всей остальной разработки.
Смысл в том, чтобы поймать проблемы установки на пустой странице, а не после дня работы.

## 11. Чек-лист заказчика

Подробная пошаговая инструкция вынесена в отдельный файл `TIMEO-SETUP.md`. Кратко:

1. Установить Claude Desktop, включить Claude Code
2. Завести GitHub и Cloudflare — нужны для блока 0
3. После первого деплоя открыть адрес на iPhone отца **в Safari** и добавить на домашний экран.
   Уведомления на этом шаге не разрешать: они появятся только в блоке 8
4. Завести Supabase — нужен к блоку 7. Выполнить присланный SQL в SQL Editor, отключить
   подтверждение почты при регистрации
5. Завести Google Cloud и создать OAuth-приложение — только если нужен вход через Google
6. Прописать адрес и анонимный ключ Supabase в переменные окружения Cloudflare Pages и пересобрать
7. Тестировать после каждого блока и присылать скриншоты

## 12. Риски

**iOS может стереть локальное хранилище.** Приложения на домашнем экране формально не подпадают под
семидневное ограничение Safari, но гарантий Apple не даёт. Смягчается облачным бэкапом и кнопкой
сохранения в файл. Запрос persistent storage вызываем, но полагаться на него нельзя: в Safari он
может просто ничего не сделать.

**Supabase засыпает через неделю бездействия.** Данные не теряются, но проект требует ручного
восстановления. Смягчается keep-alive воркером и тем, что приложение работает офлайн и без облака.

**Уведомления на iOS нельзя проверить удалённо.** Работают только после установки на домашний экран
и явного разрешения. Проверяется только на устройстве отца.

**Тестирование идёт через посредника.** Разработчик не видит экран и не может нажать кнопку.
Каждый круг правок упирается в скорость обратной связи.
